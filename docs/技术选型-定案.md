# bili_fans 技术选型（正式定案）

> 2026-10-04 定案。前序讨论见 `技术选型-头脑风暴.md`。
> 本文档是正式开发的锚：技术栈、项目结构、服务边界、部署拓扑。

## 一、定案总览

| 层 | 选型 | 说明 |
|---|---|---|
| 前端框架 | **Nuxt 4**（SSR 模式） | 用户主导设计；Vue3 生态；SSR 解锁 UP 主页 SEO |
| UI 方案 | **Tailwind CSS + headless 组件（Reka UI / Radix Vue 系）** | 自建设计语言，不用 Element Plus 类模板答案（用户强设计向） |
| 后端框架 | **FastAPI**（Python 3.11+） | bili_client 同语言直接并入；OpenAPI 类型同步；async 适配轮询/调度 |
| 数据库 | **MySQL 8** + SQLAlchemy 2.0 + Alembic | 已有规划；ORM 带迁移管理 |
| 取数核心 | **bili_client.py 并入后端进程（A1 单体起步）** | 14,213 次请求验证的资产；代码上预留 A2（独立取数服务）切分线 |
| 调度/限速 | 自研令牌桶（全局唯一 B 站出口）+ APScheduler | 风控包络 0.2~0.67 req/s 硬约束；五模式更新机制（更新机制设计稿）即任务队列 |
| 部署 | 香港（宝塔）：Nuxt 走 PM2，FastAPI 走 systemd，Nginx 反代 | 深圳待命；浙江不续费 |
| 类型同步 | FastAPI OpenAPI → `nuxt-open-fetch` / `openapi-typescript` | 后端改字段，前端编译期报错 |
| 凭证安全 | 用户 B 站 Cookie：cryptography(Fernet) 加密落库，密钥环境变量 | 绝不上深圳/任何测试服务器（纪律⑥） |

## 二、"全部用 Python 吗？"——不用，边界如下

- **Python 只做后端**：API、bili_client、调度器、令牌桶、DB。这是现有 Python 资产的天然归宿
- **前端 TS/Vue（Nuxt4）**：UI 主权完全归用户（强设计向前端 + 想尝鲜 Nuxt4）
- **连接件**：Nuxt Nitro server 反代 `/api/**` → FastAPI（浏览器全同源，FastAPI 免 CORS；session/凭证走 httpOnly cookie）

## 三、项目结构（monorepo，预留 A2 切分线）

```
bili_fans/
├── frontend/                # Nuxt4（用户主权区）
│   ├── app/                 # pages / components / layouts / assets
│   ├── server/              # Nitro：/api/** 反代到 FastAPI
│   └── nuxt.config.ts
├── backend/                 # FastAPI（AI 主权区）
│   ├── app/
│   │   ├── main.py          # FastAPI 入口
│   │   ├── api/             # 路由：auth / ups / records / bili_oauth / admin
│   │   ├── core/            # 配置、加密(Fernet)、依赖注入
│   │   ├── models/          # SQLAlchemy 模型
│   │   ├── schemas/         # Pydantic（= OpenAPI = 前端类型源）
│   │   └── services/
│   │       ├── bili/        # ★ bili_client.py 迁入（核心资产，整文件保留）
│   │       ├── scheduler/   # 令牌桶 + APScheduler + 五模式任务队列
│   │       └── sync.py      # A1↔A2 切分线：所有取数调用只经此模块
│   ├── alembic/             # DB 迁移
│   └── pyproject.toml
└── docs/                    # 本文档族（NOTES.md 等）
```

**切分纪律**：主站任何代码不得直接调 `services/bili/`，一律经 `services/sync.py`——未来拆独立取数服务时只动这一个模块。

## 四、关键功能的技术映射

| 功能 | 实现 |
|---|---|
| 用户扫码登录 B 站 | FastAPI 生成 qrcode_key 会话 → Nuxt 渲染二维码 → 前端 2s 轮询状态 API（复用已验证 poll 逻辑）→ SESSDATA 加密落库 |
| 关注列表导入 | 授权后异步任务：全量拉取（15s/895条）→ 进度状态文件落盘（已验证模式，不用日志流）→ 前端轮询进度 |
| 老粉识别 | contracts_all() + 粉丝数 24h 缓存（PoC 缓存策略平移） |
| UP 数据供给 | MySQL 读；fetched_at 过时 → 触发更新机制（五模式设计稿） |
| 全局限速 | 令牌桶单点：所有 B 站请求过 `services/sync.py`，包络内速率可配置 |
| 变更时间线 | card 刷新时检测头像/签名变更 → 事件表（数据血缘 source 列） |
| 管理面板 | Nuxt 内 admin 路由组（用户主导设计，不做 Django admin 式将就） |

## 五、部署拓扑（香港单节点）

```
用户 → Nginx(443, com域名)
        ├── /            → Nuxt SSR (PM2, :3000)
        └── /api/**      → FastAPI (systemd, :8000)
                              ├── MySQL(本机)
                              └── B站出口(令牌桶 0.2~0.67 req/s)
深圳：取数备份节点，待命（F 阶段 ping 数据定回传方案）
```

- Nuxt4 要求 Node 20+（宝塔/nvm）
- 测试期间 server_test/ 的身份文件、PoC 凭证不入生产目录
