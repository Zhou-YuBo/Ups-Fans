# 更新机制设计 — 用户构思复述与建议（2026-08-30）

> 状态：讨论稿。来源：用户口述构思 + AI 复述/评注。待用户逐条确认后成为正式设计。

## 一、用户构思复述

### 静态基础
- MySQL 已存几千个 UP 主档案（粉丝数等字段 + 应有 fetched_at 时间戳）
- 管理员（站长本人）需要一个可视化管理面板：实时查看表格状态、条件筛选、人工判定哪些 UP 需要更新、发起更新程序、设置参数（具体功能待商榷）

### 五种更新触发模式
1. **快速替换**（管理员发起）：以较小间隔把选中的 UP 全部更新完，追求尽快
2. **匀摊替换**（管理员发起）：指定总时长（如 2 天），把选中 UP 均摊到时间轴上，以较大间隔缓慢完成
3. **过期标记自动批量**：UP 超过 X 时间未更新 → 打标记；被标记数 ≥ N → 自动发起一轮替换，兜底站长遗漏
4. **用户点击触发**：网站用户在前台点击 → 服务器为该行为单独发起一次更新；需要一套控制方案（防短时大量刷新、防单日/单周总量过大、防与后台高频轮询叠加冲突），细节后议
5. **个人电脑代刷**（自称"不正经"）：站长个人电脑（家宽/校园网，IP 信誉优于机房）运行更新程序，结果手动提交给 MySQL，视同一次刷新

### 边界共识
- 浏览器端直连 B 站取数已被实测否决（Origin 白名单 403 + JSONP 已死），用户设备发起问询的方案否定；仅服务器 + 个人电脑发起，足够运营
- 每个 UP 变化的不只是粉丝数（头像/签名等可被 UP 手动改），但**不为这些字段单独立自动化**——顺带更新即可
- 远期：开发 B 站配套插件减少用户两站切换；插件内放开关"是否愿意帮助刷新 UP 主数据"，自愿用户参与取数（第五模式的分布式复活，用户主动同意版）

## 二、AI 评注（逐模式）

| 模式 | 评注 |
|---|---|
| 1 快速 | 上限受风控预算约束，不是想多快就多快。已校准 0.67 req/s 全绿；"快速档"建议先定 ~1 req/s，待轮次4阶梯校准后放行更高 |
| 2 匀摊 | 与 1 是**同一个执行器的不同速率参数**，不是两套程序。几千 UP @0.67 req/s 全量一轮 ≈ 1.5~2.5 小时 |
| 3 过期标记 | 方向对，与"冷数据自适应保底"同构。建议过期阈值按 UP 活跃度分层（活跃号短、死号长）；并在"N 个标记"之外加时间兜底（如距上次批量 >48h 且存在过期 UP 也自动跑），防止 N 攒不满时永久搁置 |
| 4 用户点击 | 核心设计：**所有模式共享同一个出站队列 + 全局速率总闸（令牌桶）**，用户请求只是"插队到队头的高优先级任务"，而非独立通道——叠加冲突问题在此自然消解。前端先查 fetched_at，太新直接回库值（大部分点击被吸收）；同 UP 并发刷新合并为一次任务 |
| 5 个人电脑 | 不"不正经"，是合法运维手段。但**强烈建议：PC 程序走服务器 admin 回填 API（带来源标记），绝不直连 MySQL**——公网开 MySQL 端口是安全雷区，且绕过校验层会埋数据雷。手动提交也过一遍合理性校验 |

## 三、AI 补充建议

1. **统一执行器模型**：模式 1/2/3/4 全部归结为"任务队列 + 优先级 + 速率控制器"。管理面板新增最有价值的一块：队列深度 / 当前出站速率 / 今日已用量实时显示
2. **数据血缘**：每次刷新记录 source 字段（fast / spread / stale_auto / user_click / manual_pc / plugin），审计、调试、评估各通道贡献全靠它
3. **单次刷新拉多字段**：relation/stat + card 两个轻接口（合计 2 请求/UP）顺带把头像/昵称/签名/等级/认证全刷掉，头像变更检测零成本顺带解决；acc/info 仍是重接口，只用于详情页深度刷新，不进常规批量
4. **签名/头像变更即事件**：对"记录与 UP 之间的故事"的平台，"这个 UP 改签名了"本身就是有价值的内容素材（card 接口免费给），建议入库为变更时间线，后期再考虑是否展示（防 UP 把签名当日更计数器的噪音）
5. **插件开关的前提提醒**：插件 background 脚本带 host_permissions，确实不受 CORS 限制（"浏览器路径被阻断"只对纯网页成立、对扩展不成立），技术上可行。但它的价值 ∝ 活跃用户量，冷数据保底服务器自己就够了——定位为"用户参与感 + 锦上添花"，不做架构依赖；默认关闭、明确告知、服务器端照常做合理性校验（客户端数据一律不可信）
6. **管理面板最小集先行**：表格 + 条件筛选（按 fetched_at 排序即"谁最旧"）+ 勾选批量发起 + 队列状态监视，其余后加
7. **校准仍需继续**：轮次 2（2h）、轮次 3（8h 过夜）照计划执行——所有模式的速率上限最终都由校准数据说话；快速档若想提速，靠轮次 4 阶梯测试找悬崖
